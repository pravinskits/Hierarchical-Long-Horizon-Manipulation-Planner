# Experimental Results

This document summarizes the final evaluation results generated by the Phase 13 integration benchmark.

## Methodology

The evaluation uses the PyBullet simulation environment to run a randomized suite of long-horizon tasks across different seeds, varying the **task horizon** (number of sequential subgoals) and the **failure rate** (probability of a mechanical fault like a slipped grasp).

We compared four ablation systems:
1. **OPEN_LOOP**: No monitoring. Assumes every skill succeeds.
2. **HIERARCHICAL_NO_RECOVERY**: Validates plans hierarchically and monitors skills, but aborts on the first failure.
3. **HIERARCHICAL_SIMPLE_RETRY**: Detects failures and blindly retries the exact same action, without classification.
4. **FULL_ADAPTIVE_RECOVERY**: Detects failures, classifies them (e.g. `Collision`, `Grasp_Failure`), and dynamically escalates recovery strategies.

## Benchmark Configuration
- **Horizons**: 5, 10, 20
- **Failure Rates**: 0.0 (0%), 0.10 (10%), 0.20 (20%)
- **Seeds**: 1, 2, 3
- **Total Iterations**: 108 distinct simulation runs.

## Key Findings

### 1. Task Success vs Horizon
As the task horizon increases to 20, systems without adaptive recovery approach a 0% success rate, due to compound error probability. The `FULL_ADAPTIVE_RECOVERY` system significantly mitigates this drop, maintaining task completion even in 20-step tasks.

### 2. Error Propagation
Open loop systems propagate errors indefinitely (e.g. attempting to move a block that was never grasped). `FULL_ADAPTIVE_RECOVERY` reduces error propagation to near zero, as failures are detected exactly when they occur and are either resolved or safely aborted.

### 3. Recovery Efficiency
`FULL_ADAPTIVE_RECOVERY` requires fewer average recovery attempts than `HIERARCHICAL_SIMPLE_RETRY` because it intelligently escalates to re-grasping or re-planning, rather than continually retrying a doomed trajectory.
